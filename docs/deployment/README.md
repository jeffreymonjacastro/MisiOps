# Deployment Runbook: MisiOps on AWS

How the MisiOps environments are built, deployed, verified, rolled back and observed. Feature: [specs/012-aws-deployment](../../specs/012-aws-deployment/spec.md). Infrastructure code: [`infra/`](../../infra/). Resource contract: [cdk-stacks.md](../../specs/012-aws-deployment/contracts/cdk-stacks.md). Workflow contract: [deploy-workflow.md](../../specs/012-aws-deployment/contracts/deploy-workflow.md).

## Overview

```text
GitHub (push to develop / main)
  └─ devsecops workflow: builds linux/arm64 images once, scans them, stores them as the `images` artifact
       └─ deploy workflow (workflow_run, only after a successful push pipeline)
            ├─ OIDC → IAM role MisiOpsGithubDeploy (short-lived credentials, no stored keys)
            ├─ docker load + push to ECR misiops-backend / misiops-frontend, tag = commit SHA (immutable)
            ├─ cdk deploy MisiOps-<env>  (dev: automatic · prod: waits for the reviewer of the GitHub Environment)
            └─ smoke test against the public URL

Internet ──HTTPS──> CloudFront (*.cloudfront.net, no caching except /_next/static/*)
                      └─HTTP──> ALB (public subnets)  /api/*, /openapi.json, /docs, /redoc ──> backend task :8000 (Fargate ARM64)
                                                        everything else ───────────────────> frontend task :3000 (Fargate ARM64)
                                                                                                backend ──5432──> Aurora Serverless v2 PostgreSQL 16
                                                                                                                 (isolated subnets, 0–1 ACU, pauses after 10 min)
Secrets Manager: misiops/<env>/db (generated by the cluster), misiops/<env>/app (SECRET_KEY) → injected as ECS secrets
CloudWatch Logs: /misiops/<env>/backend, /misiops/<env>/frontend (30 days) · Budget: 60 USD/month per environment
```

Two stacks, region `us-east-1`:

| Stack | Deployed by | Contains |
| --- | --- | --- |
| `MisiOps-Foundation` | an administrator, once | GitHub OIDC provider, deploy role `MisiOpsGithubDeploy`, ECR repositories |
| `MisiOps-dev`, `MisiOps-prod` | the `deploy` workflow | VPC, Aurora Serverless v2, secrets, ECS cluster and services, ALB, CloudFront, log groups, budget |

`dev` and `prod` are the same code; only `env` differs (see `infra/lib/config.ts`: removal policy, deletion protection, label). Only `dev` is live today; see [Creating prod later](#creating-prod-later).

## Prerequisites

Node 20, pnpm 9.6.0, Docker, AWS CLI v2, `jq`. An AWS administrator profile is needed only for the one-time steps below; day-to-day deployments need no local credentials.

## One-time account preparation (administrator)

Run from `infra/` with an administrator profile. These steps give the account a CDK bootstrap and the Foundation stack. **No AWS access key is ever stored in GitHub**: the workflow proves its identity with OIDC and receives one-hour credentials for the role below.

```bash
cd infra && pnpm install --frozen-lockfile
AWS_PROFILE=admin pnpm cdk bootstrap aws://<ACCOUNT_ID>/us-east-1
AWS_PROFILE=admin pnpm cdk deploy MisiOps-Foundation --require-approval never --outputs-file foundation.json
jq . foundation.json      # DeployRoleArn, BackendRepositoryUri, FrontendRepositoryUri
```

Then, as repository owner (Settings):

1. **Variables → Actions** (plain variables, not secrets): `AWS_ACCOUNT_ID` = the account id, `AWS_DEPLOY_ROLE_ARN` = `DeployRoleArn` from the outputs, `ALERT_EMAIL` = the address that receives budget alerts.
2. **Environments**: see [Approving a production deployment](#approving-a-production-deployment) for `dev` and `prod`.
3. **Branches → develop → required status checks**: add `infra-ci` (the offline test + synth gate of `infra/`).

Accepted risk (research R9): the CDK bootstrap CloudFormation execution role keeps CDK's default `AdministratorAccess`. The deploy role itself can only assume the bootstrap roles, push to the two ECR repositories and describe stacks. Follow-up: re-bootstrap with `--cloudformation-execution-policies` scoped to the services this app uses. Owner: repository owner; review before the first `prod` deployment.

## How a merge becomes a deployment

1. A pull request is merged into `develop` (or `main`).
2. `devsecops` runs on the push. On `develop` the gates are report-only (EX-001); on `main` they block.
3. When `devsecops` completes, `deploy` starts. Its `resolve` job maps `develop → dev` and `main → prod`, and only continues when the pipeline run **succeeded** and was a **push** (pull requests and manual dispatches never deploy).
4. The `deploy` job downloads that run's `images` artifact (never rebuilds), pushes both images to ECR as `<commit sha>`, runs `cdk deploy MisiOps-<env>` and the smoke test, and writes a summary: environment, commit, both image digests, public URL, smoke result, duration.
5. Deployments to the same environment queue behind each other (`concurrency: deploy-<env>`); a running one always finishes.

The artifact lives for one day. A `deploy` re-run after that fails on the download step by design; re-run the `devsecops` workflow instead, which rebuilds and rescans the same commit and triggers `deploy` again.

## Approving a production deployment

GitHub Environments (owner, Settings → Environments):

| Environment | Deployment branches | Required reviewers |
| --- | --- | --- |
| `dev` | `develop` only | none |
| `prod` | `main` only | repository owner (enable "Prevent self-review") |

The deployment-branch rule matters for security: a job inside an environment presents the OIDC subject `repo:<owner>/<repo>:environment:<name>` with no branch in it, so the rule is what guarantees that only `main` can reach `prod` and only `develop` can reach `dev` (FR-012).

A push to `main` whose pipeline passes creates a `deploy` run that waits in `prod` until a reviewer approves it in the Actions UI; the approver is recorded in the run. The first approved run creates the `MisiOps-prod` stack; no code change is needed. A pending approval expires after 30 days.

## Automatic rollback

Each ECS service runs with the deployment circuit breaker and `rollback: true`, `minHealthyPercent: 100`, `maxHealthyPercent: 200`: the new task starts next to the old one and only replaces it after passing the target group health check (`GET /` → 200, every 30 s, 2 consecutive successes). If the new version keeps failing, ECS rolls the service back to the previous task definition, CloudFormation marks the stack `UPDATE_ROLLBACK_COMPLETE`, `cdk deploy` exits non-zero and the `deploy` run is red. Users keep being served by the previous version throughout. Infrastructure changes that fail to apply are rolled back by CloudFormation the same way.

Where to look: Actions → the red `deploy` run (CloudFormation error in the `cdk deploy` step); ECS console → cluster → service → *Deployments* and *Events* (circuit breaker messages); `aws ecs describe-services --cluster <ClusterName> --services <BackendServiceName>`.

## Manual rollback

Redeploy the previous good commit through the same path, never by rebuilding or by console actions:

1. Actions → `devsecops` → open the last successful run **of the commit you want back** → *Re-run all jobs*. It rebuilds and rescans that commit and uploads a fresh `images` artifact.
2. `deploy` fires automatically when it completes and redeploys that commit to the environment of the branch (`develop → dev`, `main → prod`, with approval).

Equivalent from a workstation with an administrator profile, if an image for that commit is still in ECR:

```bash
cd infra && pnpm cdk deploy MisiOps-dev -c env=dev -c imageTag=<previous sha> -c alertEmail=<email> --require-approval never
```

If the smoke test fails after a successful stack update, the environment stays on the new version and the run is red; roll back manually as above.

## Reading logs

Both services write to CloudWatch Logs, one group per environment and service, retained for 30 days (stack outputs `BackendLogGroup`, `FrontendLogGroup`):

```bash
aws logs tail /misiops/dev/backend --since 10m --follow
aws logs tail /misiops/dev/frontend --since 10m
```

Console: CloudWatch → Log groups → `/misiops/dev/backend`. Log lines appear within a minute of the request. Logs hold the applications' own output (access lines, errors), never secret values.

## Verifying a deployment

The `deploy` job runs `infra/scripts/smoke.sh <PublicUrl>`: `GET /` must be 200 and contain `MisiOps`, `GET /openapi.json` must be 200 and contain `"openapi"`, and 20 sequential requests to each must have a p95 ≤ 2 s. Run it yourself against any environment:

```bash
bash infra/scripts/smoke.sh https://<distribution>.cloudfront.net
```

Traceability check (SC-003): the digest printed in the `deploy` summary equals

```bash
aws ecr describe-images --repository-name misiops-backend --image-ids imageTag=<sha> --query 'imageDetails[0].imageDigest'
```

## Costs and budget alerts

Each environment creates an AWS Budget `misiops-<env>` of 60 USD/month that e-mails `ALERT_EMAIL` at 80 % actual spend and at 100 % forecast spend. It only notifies; nothing is ever destroyed automatically. Today the budget measures the whole account; activate cost-allocation tags (`Project`, `Environment`) in Billing to filter it later.

Idle estimate per environment (no user requests; only the ALB health checks every 30 s and the database paused): ALB ≈ 16 USD, two ARM Fargate tasks ≈ 14 USD, four public IPv4 addresses ≈ 15 USD, Secrets Manager ≈ 1 USD, Aurora storage ≈ 1–2 USD, CloudFront within the free tier → **≈ 48 USD/month**. Database compute is billed only while active (0.5–1 ACU ≈ 0.06–0.12 USD/hour); the first request after a pause takes up to 30 s.

## Local development is unchanged

`docker/docker-compose.yaml` builds the frontend with `NEXT_PUBLIC_API_BASE_URL=http://localhost:8000` (build argument); the cloud image uses the Dockerfile default `""` and calls the API through relative paths on the same origin. The `dev` banner and the ` · dev` title suffix appear only when the container has `APP_ENV=dev`; local runs and tests show no label.

## Infrastructure changes

Edit `infra/`, open a pull request to `develop`: `infra-ci` runs the stack tests and an offline synth of `dev` and `prod` (no credentials). After the merge the normal pipeline deploys the change to `dev`; an infrastructure-only change still goes through `devsecops` and reuses its images.

```bash
cd infra && pnpm install --frozen-lockfile
pnpm test
pnpm synth -c env=dev -c imageTag=ci -c alertEmail=ci@example.com
```

When credentials are present (the deploy job, or your workstation) the CDK CLI performs one availability-zone lookup through the bootstrap lookup role and writes `infra/cdk.context.json`; the file is git-ignored and safe to delete. In CI no account is resolved, so the synth runs fully offline.

## Tearing down dev

```bash
cd infra && pnpm cdk destroy MisiOps-dev -c env=dev -c imageTag=<sha> -c alertEmail=<email>
```

Removes compute, networking, routing, the `dev` database (no snapshot) and its log groups. ECR repositories, their images and `MisiOps-Foundation` remain. In `prod` the database is kept as a final snapshot and has deletion protection, so `cdk destroy MisiOps-prod` stops at the cluster until protection is turned off on purpose.

## Creating prod later

Nothing to code. Create the `prod` GitHub Environment as described above, merge `develop` into `main`, let `devsecops` pass in blocking mode and approve the waiting `deploy` run. That run executes `cdk deploy MisiOps-prod` with the same images.
