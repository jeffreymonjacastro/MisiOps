\section{Aplicación de Git con Conventional Commits}

\subsection{Breve explicación de qué son los Conventional Commits y por qué se usan}
\emph{Conventional Commits}\footnote{\url{https://www.conventionalcommits.org/en/v1.0.0/}} es una convención ligera para escribir mensajes de commit con una estructura fija y legible tanto por personas como por herramientas:

\begin{lstlisting}
<tipo>[ámbito opcional]: <descripción>

[cuerpo opcional]

[pie(s) opcional(es)]
\end{lstlisting}

El \textbf{tipo} dice qué clase de cambio es (una funcionalidad, una corrección, documentación...), el \textbf{ámbito} entre paréntesis acota la parte del sistema afectada (en nuestro monorepo: \texttt{backend}, \texttt{frontend}, \texttt{specs}, \texttt{ci}), la \textbf{descripción} resume el cambio en imperativo y en una línea, el \textbf{cuerpo} explica el porqué y el \textbf{pie} enlaza issues o marca cambios incompatibles (\texttt{BREAKING CHANGE:} o un \texttt{!} después del tipo).

En MisiOps se adoptó por cuatro razones:

\begin{itemize}
    \item \textbf{Trazabilidad}: con tres personas trabajando en paralelo, \texttt{git log --oneline} se lee como un registro de cambios y permite saber qué entró en cada rama sin abrir los diffs.
    \item \textbf{Relación con el flujo SDD}: cada funcionalidad produce primero commits \texttt{docs(specs)} y después commits \texttt{feat}; el historial refleja el orden del pipeline.
    \item \textbf{Revisión más rápida}: el tipo en el asunto indica al revisor qué esperar del PR y cuánto riesgo tiene (un \texttt{chore} no se revisa igual que un \texttt{feat} de 900 líneas).
\end{itemize}

La convención se refuerza con dos \emph{skills} del repositorio (\texttt{commit\allowbreak-message\allowbreak-writer} y \texttt{git\allowbreak-change\allowbreak-publisher}), que analizan los cambios preparados en el área de \emph{staging} y ayudan a redactar y publicar el commit, además de una plantilla de Pull Request obligatoria en \texttt{.github/\allowbreak pull\_request\_template.md}.

\subsection{Guía de tipos principales}
\begin{itemize}
    \item \texttt{feat}: nueva funcionalidad visible para el usuario o para otro componente (un endpoint, una pantalla, el stack de Compose).
    \item \texttt{fix}: corrección de un comportamiento incorrecto; el cuerpo describe el síntoma y la causa raíz.
    \item \texttt{docs}: documentación, especificaciones en \texttt{specs/}, plantillas de PR, README. En SDD son los commits que preceden a todo \texttt{feat}.
    \item \texttt{test}: se agregan o corrigen pruebas sin cambiar el código de producción.
    \item \texttt{chore}: mantenimiento que no afecta el comportamiento (lockfiles, configuración de herramientas).
    \item \texttt{ci}: cambios en los workflows de GitHub Actions o en hooks de Git.
    \item \texttt{refactor}: reestructuración interna sin cambio funcional ni corrección.
\end{itemize}

\subsection{Captura de Pull Requests}
El equipo sigue GitFlow: \texttt{main} solo recibe \emph{merges} desde \texttt{develop} siendo la rama de integración. El trabajo comienza en ramas \texttt{feature/<nombre>} creadas desde \texttt{develop}; cuando una funcionalidad depende de otra aún no integrada, la rama dependiente se crea a partir de la primera y se usan \emph{PRs apilados}. Por ejemplo, el PR~\#11 (\texttt{feature/user-auth}) apunta a \texttt{develop}, el PR~\#12 (\texttt{feature/categories}) apunta a la rama de \#11 y el PR~\#13 (\texttt{feature/transactions}) apunta a la rama de \#12. El frontend siguió el mismo patrón con una pila lineal de seis PRs (\#5 $\rightarrow$ \#6 $\rightarrow$ \#7 $\rightarrow$ \#8 $\rightarrow$ \#9 $\rightarrow$ \#10), donde cada uno apunta a la rama del anterior. Tras fusionar cada PR, se actualiza manualmente la rama base del siguiente para que apunte a su nueva base. La Tabla~\ref{tab:prs} resume los 18 PRs del proyecto.
