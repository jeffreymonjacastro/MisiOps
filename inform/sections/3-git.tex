\section{Aplicación de Git con Conventional Commits}

\subsection{Breve explicación de qué son los Conventional Commits y por qué se usan}
\emph{Conventional Commits}\footnote{\url{https://www.conventionalcommits.org/en/v1.0.0/}} es una convención ligera para escribir mensajes de commit con una estructura fija y legible tanto por personas como por herramientas:

\begin{lstlisting}
<tipo>[ámbito opcional]: <descripción>

[cuerpo opcional]

[pie(s) opcional(es)]
\end{lstlisting}

El \textbf{tipo} dice qué clase de cambio es (una funcionalidad, una corrección, documentación...), el \textbf{ámbito} entre paréntesis acota la parte del sistema afectada (en nuestro monorepo: \texttt{backend}, \texttt{frontend}, \texttt{specs}, \texttt{ci}), la \textbf{descripción} resume el cambio en imperativo y en una línea, el \textbf{cuerpo} explica el porqué y el \textbf{pie} enlaza issues o marca cambios incompatibles (\texttt{BREAKING CHANGE:} o un \texttt{!} después del tipo).

En MisiOps se adoptó por cuatro razones:

\begin{itemize}
    \item \textbf{Trazabilidad}: con tres personas trabajando en paralelo, \texttt{git log --oneline} se lee como un registro de cambios y permite saber qué entró en cada rama sin abrir los diffs.
    \item \textbf{Relación con el flujo SDD}: cada funcionalidad produce primero commits \texttt{docs(specs)} y después commits \texttt{feat}; el historial refleja el orden del pipeline.
    \item \textbf{Automatización}: la convención mapea directamente a versionado semántico (\texttt{fix} $\rightarrow$ PATCH, \texttt{feat} $\rightarrow$ MINOR, \texttt{BREAKING CHANGE} $\rightarrow$ MAJOR) y permite generar \emph{changelogs} de forma automática más adelante.
    \item \textbf{Revisión más rápida}: el tipo en el asunto indica al revisor qué esperar del PR y cuánto riesgo tiene (un \texttt{chore} no se revisa igual que un \texttt{feat} de 900 líneas).
\end{itemize}

La convención se refuerza con dos \emph{skills} del repositorio (\texttt{commit-message-writer} y \texttt{git-change-publisher}) que generan el mensaje a partir del \emph{staging area}, y con una plantilla de Pull Request obligatoria en \texttt{.github/pull\_request\_template.md}.

\subsection{Guía de tipos principales}
\begin{itemize}
    \item \texttt{feat}: nueva funcionalidad visible para el usuario o para otro componente (un endpoint, una pantalla, el stack de Compose).
    \item \texttt{fix}: corrección de un comportamiento incorrecto; el cuerpo describe el síntoma y la causa raíz.
    \item \texttt{docs}: documentación, especificaciones en \texttt{specs/}, plantillas de PR, README. En SDD son los commits que preceden a todo \texttt{feat}.
    \item \texttt{test}: se agregan o corrigen pruebas sin cambiar el código de producción.
    \item \texttt{chore}: mantenimiento que no afecta el comportamiento (lockfiles, configuración de herramientas).
    \item \texttt{ci}: cambios en los workflows de GitHub Actions o en hooks de Git.
    \item \texttt{refactor}: reestructuración interna sin cambio funcional ni corrección.
\end{itemize}

\subsubsection*{Análisis detallado de seis commits}
Se eligieron dos commits de cada área (backend, frontend e infraestructura), cada par perteneciente a un mismo Pull Request para mostrar cómo conviven un \texttt{feat} con su \texttt{fix} o \texttt{ci} de acompañamiento.

\paragraph{1. \texttt{df48f7d} --- feat(backend): add transaction endpoints, summary and category guards} (Gabriel Espinoza, PR \#13).
\textbf{Tipo}: \texttt{feat}, porque introduce capacidad nueva: la tabla \texttt{transactions}, los endpoints \texttt{POST/GET /api/v1/transactions} con paginación por \emph{offset} y filtros, \texttt{GET /transactions/summary} con desglose por categoría, y \texttt{PATCH/DELETE} por id. \textbf{Ámbito}: \texttt{backend}. \textbf{Impacto}: 885 líneas en 11 archivos, incluidas 55 pruebas nuevas; añade además las ``guardas'' en categorías que rechazan cambiar el tipo o borrar una categoría con transacciones (409). Es el commit que cierra la API mínima que el frontend necesita.

\paragraph{2. \texttt{328d288} --- fix(backend): disable session expiry on commit for async sessions} (Gabriel Espinoza, PR \#12).
\textbf{Tipo}: \texttt{fix}, porque corrige un error real: con sesiones asíncronas de SQLAlchemy, acceder a un atributo después del \texttt{commit} sobre una instancia expirada lanza \texttt{MissingGreenlet} y se traducía en un 500 al crear categorías contra Postgres. \textbf{Impacto}: 9 líneas, pero críticas; el cuerpo del mensaje documenta síntoma y causa, y se añade \texttt{test\_database.py} como prueba de regresión para que el ajuste \texttt{expire\_on\_commit=False} no se pierda.

\paragraph{3. \texttt{6601d7e} --- feat(frontend): connect the app to the backend API} (Yared Riveros, PR \#76).
\textbf{Tipo}: \texttt{feat} con ámbito \texttt{frontend}. Reemplaza el ``libro mayor'' local del navegador por llamadas a la API: agrega registro, login, logout y un guardia de rutas que adjunta el \emph{bearer token} a cada petición; mueve paginación, filtrado y agregación al servidor. \textbf{Impacto}: 30 archivos; elimina seis módulos que ya no tienen sentido (\texttt{ledger-store}, \texttt{storage}, \texttt{summary}...) y reescribe \texttt{types.ts} con las formas del servidor. El cuerpo describe la pasada de convergencia (paso 12 del SDD) que detectó y corrigió cinco brechas antes de abrir el PR.

\paragraph{4. \texttt{fa93c99} --- fix(frontend): purge the legacy local-ledger key on boot} (Yared Riveros, PR \#76).
\textbf{Tipo}: \texttt{fix}. Un navegador que usó la versión pre-backend conservaba datos reales bajo la clave \texttt{misiops.ledger.v1} de \texttt{localStorage}; nada los leía, pero tampoco nada los borraba, lo que violaba dos requisitos de la especificación (FR-012 y SC-006). \textbf{Impacto}: 38 líneas en 3 archivos; el \texttt{AppShell} barre la clave una vez al arrancar y se añaden dos pruebas. El mensaje explica además por qué la verificación original no lo detectó, información útil para quien lea el historial.

\paragraph{5. \texttt{1e9b172} --- feat: add docker compose setup for frontend, backend and postgres} (Jeffrey Monja, PR \#73).
\textbf{Tipo}: \texttt{feat} sin ámbito, porque toca todo el monorepo: crea los \texttt{Dockerfile} de backend y frontend, sus \texttt{.dockerignore}, el \texttt{docker-compose.yaml} con tres servicios, secreto de Postgres y redes pública/privada, y de paso el workflow \texttt{frontend-ci.yml}. \textbf{Impacto}: el proyecto pasa a levantarse con un solo comando. Viene acompañado de los artefactos SDD de \texttt{specs/009-docker-compose} (spec, plan, checklist, evaluación y tareas), que el \emph{enforcer} exige.

\paragraph{6. \texttt{64876cb} --- ci: add docker compose integration test workflow} (Jeffrey Monja, PR \#73).
\textbf{Tipo}: \texttt{ci}, porque solo añade un workflow de GitHub Actions. \texttt{docker-integration.yml} genera secretos de prueba, ejecuta \texttt{docker compose up --build -d}, espera al \emph{healthcheck} de Postgres, verifica con \texttt{curl} que el backend responda en \texttt{:8000} y vuelca los logs si algo falla. \textbf{Impacto}: convierte la dockerización en algo verificado en cada PR hacia \texttt{develop}, no en una promesa del README.

\subsection{Captura de Pull Requests}
El equipo sigue \textbf{GitFlow}: \texttt{main} solo recibe \emph{merges} desde \texttt{develop} (PRs \#2 y \#75, los ``checkpoints''), \texttt{develop} es la rama de integración y todo el trabajo ocurre en ramas \texttt{feature/<nombre>} creadas desde \texttt{develop}. Cuando una funcionalidad depende de otra aún no integrada se usan \emph{PRs apilados}: por ejemplo \#11 (\texttt{feature/user-auth}) apunta a \texttt{develop}, \#12 (\texttt{feature/categories}) apunta a \#11 y \#13 (\texttt{feature/transactions}) apunta a \#12; GitHub redirige la base automáticamente al fusionarse el anterior.
