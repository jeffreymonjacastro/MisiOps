\section{Conclusiones preliminares}

\subsection{Importancia de usar Git con convenciones claras para la trazabilidad}
Con tres personas trabajando en paralelo sobre frontend, backend e infraestructura, y con Pull Requests apilados (\#11 $\rightarrow$ \#12 $\rightarrow$ \#13, \#5 $\rightarrow$ \#6/\#7 $\rightarrow$ \#8 $\rightarrow$ \#9 $\rightarrow$ \#10), el historial fue la única fuente de verdad sobre qué había entrado a \texttt{develop} y en qué orden. Conventional Commits hizo que ese historial fuera legible sin abrir diffs: un \texttt{fix(backend)} de 9 líneas con su causa raíz en el cuerpo (\texttt{328d288}) ahorró a los demás volver a diagnosticar el mismo error 500. GitFlow, con \texttt{main} recibiendo solo checkpoints desde \texttt{develop}, dio una rama siempre desplegable y ramas \texttt{feature/} desechables. Aprendimos también que la convención se sostiene mejor con herramientas que con voluntad: la plantilla de PR, el hook \texttt{pre-push} y el workflow \texttt{sdd-enforcer} evitaron que llegara código sin especificación.

\subsection{Beneficio de las pruebas unitarias para la calidad y mantenibilidad}
Las 158 pruebas (119 de backend, 39 de frontend) cumplieron dos funciones. Primero, como especificación ejecutable: reglas como ``montos con más de dos decimales son 422'' o ``el periodo presupuestario empieza el día que el usuario elige'' quedaron fijadas en \texttt{parametrize} antes de que el frontend las consumiera, y sirvieron de contrato entre ambos equipos. Segundo, como red de seguridad en refactorizaciones grandes: el commit \texttt{6601d7e} borró seis módulos del frontend y reescribió los tipos; que las 39 pruebas siguieran en verde fue lo que permitió fusionarlo con confianza. Correr las pruebas contra SQLite en memoria (backend) y con el \emph{runner} nativo de Node (frontend) las mantuvo rápidas (menos de 10 segundos en total), lo que hace que realmente se ejecuten en cada cambio y en cada PR.

\subsection{Beneficio de dockerizar su aplicación}
Antes de Compose, ``levantar el proyecto'' significaba instalar Python 3.13, \texttt{uv}, Node 20, \texttt{pnpm} y un Postgres local con las credenciales correctas, y cada integrante lo tenía ligeramente distinto. Con \texttt{docker compose up --build} el entorno pasó a ser el mismo en las tres máquinas y en GitHub Actions, que ahora verifica en cada PR que el stack completo arranca y responde. El \emph{healthcheck} de Postgres y el \texttt{depends\_on} con condición eliminaron los errores de conexión por orden de arranque; la red privada interna y el secreto de Compose dejaron la base de datos inaccesible desde el host y la contraseña fuera del YAML. El costo fue moderado (dos Dockerfiles cortos y un archivo de Compose) y el retorno inmediato: los revisores pueden probar un PR sin configurar nada.
