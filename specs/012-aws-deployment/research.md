# Research: AWS Deployment for MisiOps

**Date**: 2026-11-07 | **Spec**: [spec.md](./spec.md)

Every decision below was checked against current documentation through Context7 (`/aws/aws-cdk`, `/aws-actions/configure-aws-credentials`, `/actions/download-artifact`) on 2026-11-07. Versions are pinned here and reused by `plan.md`, the contracts and `tasks.md`.

## R1. Infrastructure language and tooling

- **Decision**: AWS CDK v2 in TypeScript (`aws-cdk-lib` 2.273.0, `constructs` 10.x, CDK CLI `aws-cdk` 2.1100+ matching the lib), Node 20, pnpm 9.6.0 (same as `frontend/`), tests with `node:test` + `tsx` (same runner as `frontend/test`), assertions with `aws-cdk-lib/assertions`.
- **Rationale**: Requested by the team; TypeScript is the CDK's primary language; reusing the frontend's package manager and test runner adds zero new tooling to learn. `aws-cdk-lib/assertions` gives template-level tests for NFR-007 without deploying.
- **Alternatives considered**: CDK in Python (would match `backend/` but CDK docs and examples are TypeScript-first); Terraform (not requested, no CloudFormation rollback integration); SAM/Serverless (wrong fit for long-running containers).

## R2. Compute: ECS Fargate, two services, one cluster

- **Decision**: One `ecs.Cluster` per environment; two `ecs.FargateService`s (`backend`, `frontend`), each 0.25 vCPU / 512 MiB, `desiredCount: 1`, Linux/**ARM64** (`runtimePlatform: { operatingSystemFamily: LINUX, cpuArchitecture: ARM64 }`, Graviton, ~20 % cheaper than x86), `circuitBreaker: { enable: true, rollback: true }`, `minHealthyPercent: 100`, `maxHealthyPercent: 200`. Images from ECR by tag `imageTag` (the commit SHA) passed as CDK context. The DevSecOps `build` and `dast` jobs move to GitHub's ARM runners (`runs-on: ubuntu-24.04-arm`, free for public repositories) so the scanned and delivered images are native `linux/arm64`; `container`, `sca`, `sast` and the deploy job stay on x86 (Trivy scans and `docker load`/`push` do not execute the image). Base images are multi-arch: `python:3.13-slim`, `node:20-alpine`, and the pinned `ghcr.io/astral-sh/uv:0.12.14@sha256:1946145b…` digest is an OCI index containing `linux/arm64` (verified 2026-11-07 with `docker buildx imagetools inspect`).
- **Rationale**: Runs the already-hardened, already-scanned Dockerfiles unchanged (FR-009). The circuit breaker with rollback is the native implementation of FR-013; 100/200 healthy percent keeps the old task serving until the new one is healthy (FR-014). ARM64 by team decision (2026-11-07): cheaper and the Dockerfiles need no change; the only CI change is the runner label of two jobs, and the existing gates keep running (NFR-006).
- **Alternatives considered**: `ecs-patterns.ApplicationMultipleTargetGroupsFargateService` (one task definition for both containers, couples the two services' scaling and deploys); EKS (cost and complexity far above a student project); Lambda Web Adapter (would need image changes and breaks the start-up `create_all`); App Runner (no path routing between two services behind one origin, no VPC-isolated DB without a connector cost).
- **Alternatives for ARM builds**: QEMU `buildx --platform linux/arm64` on x86 runners (slow Node build, and the `dast` job could not run the images at speed); multi-arch images (doubles build time for no benefit, ECS only pulls one platform).

## R3. Networking: VPC without NAT, Fargate in public subnets, RDS isolated

- **Decision**: `ec2.Vpc` with fixed `availabilityZones: [us-east-1a, us-east-1b]` (a `maxAzs` lookup would write `cdk.context.json` at deploy time), `natGateways: 0`, subnets `PUBLIC` (ALB + Fargate tasks with `assignPublicIp: true`) and `PRIVATE_ISOLATED` (database). Security groups: ALB SG ingress TCP 80 from anywhere (`0.0.0.0/0`; team decision 2026-11-07, see NFR-008); service SGs ingress only from the ALB SG; database SG ingress 5432 only from the backend service SG. Two AZs are the minimum an ALB and a database subnet group accept.
- **Rationale**: A NAT gateway alone is ~32 USD/month, more than half the budget (NFR-003). Tasks need outbound internet only to pull from ECR and to write logs; a public IP plus a strict security group gives that at no cost. The database stays unreachable from the internet (FR-005), which costs nothing. Restricting the ALB to CloudFront's origin-facing prefix list was dropped: it needs `ec2.PrefixList.fromLookup`, a committed `cdk.context.json` and an account-bound CI synth; for a course demo the ALB's HTTP listener being reachable directly is an accepted simplification (NFR-008 SHOULD).
- **Alternatives considered**: Private subnets + NAT (cost); private subnets + VPC interface endpoints for ECR/Logs/Secrets Manager (4 endpoints ≈ 29 USD/month, same problem); verifying a custom origin header at the ALB (needs a plaintext secret in the template or a rotation Lambda); CloudFront prefix-list restriction (dropped, see Rationale; one-line upgrade path when hardening matters).
- **Cost note (analysis F2, 2026-11-07, revised)**: public IPv4 addresses are billed at 0.005 USD/hour each. The ALB uses two (one per AZ) and each Fargate task one: 4 × 3.65 ≈ 14.6 USD/month. Idle estimate per environment: ALB ≈ 16.4, Fargate ARM 2 × 0.25 vCPU/0.5 GiB ≈ 14.4, IPv4 ≈ 14.6, Secrets Manager 0.8, Aurora Serverless v2 paused ≈ 1–2 (storage only), CloudFront free tier → **≈ 48 USD**; a few hours of database activity per day add ≈ 2–5 USD. Under the 60 USD ceiling without any free tier.

## R4. Public entry: CloudFront in front of the ALB

- **Decision**: One `cloudfront.Distribution` per environment with a `LoadBalancerV2Origin` (`protocolPolicy: HTTP_ONLY`, port 80). Behaviours: default `*` → `CachePolicy.CACHING_DISABLED`, `OriginRequestPolicy.ALL_VIEWER_EXCEPT_HOST_HEADER`, `AllowedMethods.ALLOW_ALL`, `ViewerProtocolPolicy.REDIRECT_TO_HTTPS`; additional `/_next/static/*` → `CachePolicy.CACHING_OPTIMIZED`. Public address = the distribution's generated domain (`*.cloudfront.net`) with the default CloudFront certificate.
- **Rationale**: HTTPS on both environments at no recurring cost under the free tier (clarification Q2), no custom domain needed. Path routing between frontend and API happens at the ALB (R5), so CloudFront needs behaviours only where the cache policy differs: nothing dynamic is ever cached (FR-003: API responses not cached, headers and cookies forwarded) and Next.js's content-hashed static assets are. `REDIRECT_TO_HTTPS` implements the HTTP→HTTPS redirect of NFR-008 (also the default once the `@aws-cdk/aws-cloudfront:defaultViewerProtocolPolicyRedirectToHttps` flag is enabled; set explicitly to be independent of flags).
- **Alternatives considered**: ALB with an ACM certificate (needs a domain the team does not own); plain HTTP (rejected in clarification Q2); API Gateway in front of the API (second origin, extra cost, no benefit for same-origin routing).

## R5. Request routing at the ALB

- **Decision**: One `ApplicationLoadBalancer` (internet-facing, in the public subnets) with one HTTP:80 listener. Default action → frontend target group (port 3000, health check `GET /`). One listener rule, priority 10, path patterns `/api/*`, `/openapi.json`, `/docs`, `/redoc` → backend target group (port 8000, health check `GET /`). Target groups: `deregistrationDelay: 30 s`, health check interval 30 s, healthy threshold 2.
- **Rationale**: Same origin for app and API eliminates CORS configuration (the backend's `CORS_ORIGINS` default stays untouched) and lets the web app use relative API paths (FR-003, FR-004). One rule with five path patterns is the ALB limit per rule; four are needed. The backend's health endpoint is `GET /` on the container, reached directly by the target group, not through the path rule.
- **Alternatives considered**: Next.js `rewrites()` proxying `/api` to the backend (rewrites are resolved at build time in standalone output, so the backend address would be baked into the image, contradicting R8); two ALBs (double cost).

## R6. Database: Aurora Serverless v2 (PostgreSQL 16) scaling to zero

- **Decision**: `rds.DatabaseCluster` with `engine: DatabaseClusterEngine.auroraPostgres({ version: AuroraPostgresEngineVersion.VER_16_x })` (latest 16.x constant ≥ 16.3, required for 0 ACU), `writer: ClusterInstance.serverlessV2('writer')`, no readers, `serverlessV2MinCapacity: 0`, `serverlessV2MaxCapacity: 1`, `serverlessV2AutoPauseDuration: Duration.minutes(10)`, `storageEncrypted: true`, `backup: { retention: Duration.days(7) }`, `defaultDatabaseName: 'misiops'`, `credentials: rds.Credentials.fromGeneratedSecret('misiops', { secretName: 'misiops/<env>/db', excludeCharacters: <CDK default set, every URL-special character> })`, `vpcSubnets: isolated`, `securityGroups: [dbSg]`. `dev`: `removalPolicy: DESTROY`, `deletionProtection: false`. `prod`: `removalPolicy: SNAPSHOT`, `deletionProtection: true`. Confirmed at implementation (2026-11-08) against `aws-cdk-lib` 2.273.0: `serverlessV2MinCapacity`, `serverlessV2AutoPauseDuration` and `AuroraPostgresEngineVersion.VER_16_9` exist, and `aws rds describe-db-engine-versions` reports `ServerlessV2FeaturesSupport.MinCapacity: 0` for 16.9 in `us-east-1`; no fallback needed.
- **Rationale**: Team request (2026-11-07) to evaluate serverless databases for cost. Serverless v2 with scale-to-zero (available since late 2024) bills nothing for compute while paused and 0.12 USD per ACU-hour while active (0.5 ACU minimum when running ≈ 0.06 USD/h); for a course demo used a few hours a day that is ≈ 3–8 USD/month total, versus ≈ 15 USD for a fixed `db.t4g.micro` outside the 12-month free tier. The generated secret keeps the JSON keys `username`, `password`, `host`, `port`, `dbname` (cluster endpoint), so `backend/core/config.py` stays unchanged (R7). Resume after pause takes ≈ 15 s on the first connection; the ECS health checks hit `/` and never touch the database, so the pause does not affect deployments, and the backend's start-up `create_all` wakes the cluster on each deploy (spec Edge Cases, NFR-009 exclusion). Encryption and 7-day backups satisfy NFR-004.
- **Fallback**: if the installed CDK or the chosen engine version does not support 0 ACU, use `rds.DatabaseInstance` PostgreSQL 16 on `db.t4g.micro`, 20 GiB gp3, single AZ (≈ 15 USD/month, free for 12 months on new accounts); the surrounding stack (secret keys, security groups, task definition) is identical.
- **Alternatives considered**: Aurora DSQL (serverless Postgres-compatible with a generous free tier, but no foreign keys and no sequences, which the SQLAlchemy models and `create_all` rely on); RDS instance with scheduled stop/start (stops auto-restart after 7 days, manual toggling); Postgres in a Fargate task with EFS (no managed backups); RDS Multi-AZ (out of scope: HA); third-party serverless Postgres (not AWS).

## R7. Secrets injection into ECS

- **Decision**: Backend task definition `secrets`: `POSTGRES_USER ← ecs.Secret.fromSecretsManager(dbSecret, 'username')`, `POSTGRES_PASSWORD ← (…, 'password')`, `POSTGRES_SERVER ← (…, 'host')`, `POSTGRES_DB ← (…, 'dbname')`, `SECRET_KEY ← ecs.Secret.fromSecretsManager(appSecret)` where `appSecret` is a `secretsmanager.Secret` generated with 64 characters, no punctuation. Plain `environment`: `ACCESS_TOKEN_EXPIRE_MINUTES` only. Frontend task `environment`: `APP_ENV=<dev|prod>`, `PORT=3000`, `HOSTNAME=0.0.0.0`.
- **Rationale**: Secret values never appear in the template, the task definition or CI (FR-006, SC-005); the execution role gets `secretsmanager:GetSecretValue` on exactly these two secrets. A restart picks up a rotated password with no code change (US5 scenario 4).
- **Alternatives considered**: SSM Parameter Store SecureString (works, but RDS already produces a Secrets Manager secret); environment variables set from CI (would put secrets in CI).

## R8. Same image for every environment: runtime configuration only

- **Decision**: The frontend image is built once by the DevSecOps `build` job with no environment knowledge. Two small application changes make that possible:
  1. `frontend/Dockerfile` gets `ARG NEXT_PUBLIC_API_BASE_URL=""` + `ENV NEXT_PUBLIC_API_BASE_URL=$NEXT_PUBLIC_API_BASE_URL` before `pnpm run build`, so the cloud image uses relative API paths (`""` is not nullish, so the `??` fallback in `frontend/app/lib/api.ts` and `next.config.ts` is not taken). `docker/docker-compose.yaml` passes `build.args.NEXT_PUBLIC_API_BASE_URL=http://localhost:8000` so the local stack keeps working unchanged (FR-004). Local `pnpm dev` keeps the code fallback.
  2. The non-production label (FR-020) reads `process.env.APP_ENV` at request time in the root layout (`frontend/app/layout.tsx`, a server component): title suffix ` · dev` via `generateMetadata` and a fixed banner rendered when `APP_ENV !== 'prod'`-and-defined. Not `NEXT_PUBLIC_*`, which would be baked at build.
- **Rationale**: FR-009 forbids rebuilding per environment; anything that differs between `dev` and `prod` must be runtime configuration.
- **Known effect on DAST**: the `devsecops` `build` job builds the frontend with the default (`""`), so in the `dast` job's Compose stack (`--no-build`) the browser-side API base is same-origin on port 3000, where no API answers. ZAP's frontend baseline is passive and the API scan targets port 8000 directly, so no gate changes; the `docker-integration` workflow still builds with the Compose build argument. Documented, accepted (analysis C2).
- **Alternatives considered**: Building the frontend per environment in the deploy workflow (violates FR-009); putting the label in the CloudFront address (not possible on a generated domain, eval gap 2).

## R9. CI identity: GitHub OIDC → IAM role

- **Decision**: A one-time `MisiOps-Foundation` stack creates `iam.OidcProviderNative` for `https://token.actions.githubusercontent.com` (audience `sts.amazonaws.com`) and an `iam.Role` assumed by `iam.OpenIdConnectPrincipal` with conditions `StringEquals aud = sts.amazonaws.com` and `StringLike sub ∈ { repo:jeffreymonjacastro/MisiOps:ref:refs/heads/develop, repo:jeffreymonjacastro/MisiOps:ref:refs/heads/main, repo:jeffreymonjacastro/MisiOps:environment:dev, repo:jeffreymonjacastro/MisiOps:environment:prod }`. Role policy: `sts:AssumeRole` on the CDK bootstrap roles (`arn:aws:iam::<account>:role/cdk-hnb659fds-*-role-<account>-<region>`), ECR push/pull on the two repositories, `ecr:GetAuthorizationToken`, `cloudformation:DescribeStacks`. Max session 1 hour. The workflow uses `aws-actions/configure-aws-credentials@v6.3.0` with `permissions: id-token: write`.
- **Rationale**: Short-lived, per-run credentials bound to this repository and branches (FR-011, FR-012); no secret stored anywhere, only the role ARN as a repository variable. When a job runs inside a GitHub Environment, the token's `sub` is `repo:…:environment:<name>`, hence both condition forms. Because the `environment:` form carries no branch, each GitHub Environment MUST set its "Deployment branches" rule to the single allowed branch (`dev` → `develop`, `prod` → `main`); otherwise any branch declaring `environment: dev` could assume the role (analysis F1, FR-012 second sentence).
- **Alternatives considered**: IAM user access keys (forbidden by the constitution); the deprecated custom-resource `OpenIdConnectProvider` (CDK recommends `OidcProviderNative`); a role per environment (more moving parts; the deploy permissions are the same set).
- **Accepted risk**: the CDK bootstrap CloudFormation execution role keeps CDK's default `AdministratorAccess`; tightening it with `--cloudformation-execution-policies` is a documented follow-up, not in scope. Owner: repository owner; review date: before the first `prod` deployment.

## R10. Image registry

- **Decision**: Two `ecr.Repository`s in `MisiOps-Foundation` (`misiops-backend`, `misiops-frontend`), `imageScanOnPush: true`, `imageTagMutability: IMMUTABLE`, lifecycle rule keep the last 20 images, `removalPolicy: RETAIN`. Tags are the full commit SHA. The deploy workflow `docker load`s the DevSecOps `images` artifact, retags and pushes; the push output's digest is recorded in the job summary (SC-003).
- **Rationale**: Shared across environments because `dev` and `prod` run the same bytes; immutable tags make "which commit is running" unambiguous. GHCR publishing by `devsecops.yml`'s `deliver` job stays as is (NFR-006).
- **Alternatives considered**: Pulling from GHCR directly from ECS (needs a registry credential secret in Secrets Manager and only exists for `main`); one repository with tag prefixes (lifecycle rules harder to reason about).

## R11. Deploy workflow trigger and chaining

- **Decision**: New `.github/workflows/deploy.yml`, `on: workflow_run: workflows: [devsecops], types: [completed], branches: [develop, main]`. A first job maps `github.event.workflow_run.head_branch` to `dev`/`prod` and exits early unless `conclusion == 'success'` and `event == 'push'`. The deploy job uses `environment: ${{ env }}` (GitHub Environments `dev`, no reviewers; `prod`, required reviewer = repository owner), `concurrency: { group: deploy-<env>, cancel-in-progress: false }`, checks out `workflow_run.head_sha`, downloads the `images` artifact with `actions/download-artifact@v8` + `run-id: ${{ github.event.workflow_run.id }}` + `github-token: ${{ secrets.GITHUB_TOKEN }}` (`permissions: actions: read`).
- **Rationale**: `workflow_run` is the only trigger that fires after another workflow finishes and exposes its run id; the artifact download with run id reuses the exact scanned images (FR-009). `cancel-in-progress: false` lets an in-flight deployment finish and keeps only the newest pending one (FR-015). GitHub Environments give the approval gate (FR-010) and the per-environment OIDC `sub` (R9). On `develop` the DevSecOps gates are report-only, so `conclusion == success` means "pipeline completed" (constitution Deployment Environments); on `main` it means every gate passed.
- **Alternatives considered**: Adding a deploy job inside `devsecops.yml` (mixes scanning and deploying, and the DevSecOps workflow's `permissions: contents: read` would need `id-token: write`); `workflow_call` reusable workflows (would require restructuring `devsecops.yml`, violating NFR-006's spirit); `dawidd6/action-download-artifact` (third-party; the official action now supports `run-id`).
- **Known limit**: the DevSecOps `images` artifact has `retention-days: 1`; the deploy runs minutes later, and a manual re-run after a day fails on download by design (FR-009 edge case). Re-running the DevSecOps workflow regenerates it. The artifact name `images` and the files `backend.tar` / `frontend.tar` are a contract between the two workflows: renaming them in `devsecops.yml` breaks `deploy.yml`, so both files change together.

## R12. Infrastructure CI and tests

- **Decision**: New `.github/workflows/infra-ci.yml` on `pull_request` and `push` to `develop` with `paths: ["infra/**"]`: `pnpm install --frozen-lockfile`, `pnpm test` (node:test + assertions), `pnpm synth` (`cdk synth --all -c env=dev -c imageTag=ci -c alertEmail=ci@example.com`, no credentials, no account variable). Required status check on `develop`.
- **Rationale**: FR-007 and NFR-007. With the prefix-list lookup dropped (R3) the stacks contain no context lookups, so `cdk synth` in CI needs neither credentials nor an account id: the stack is environment-agnostic at synth time (`account` resolved at deploy by the OIDC role) and region is fixed in code (`us-east-1`). No `cdk.context.json` is committed and no `AWS_ACCOUNT_ID` variable is required by CI (analysis C1 resolved by removal).
- **Tests (NFR-007)**: zero NAT gateways; `AWS::RDS::DBCluster` with `ServerlessV2ScalingConfiguration: { MinCapacity: 0, MaxCapacity: 1 }`, `StorageEncrypted: true`, `BackupRetentionPeriod ≥ 7`, subnets from the isolated group, and its `AWS::RDS::DBInstance` `DBInstanceClass: db.serverless`, `PubliclyAccessible: false`; both task definitions `RuntimePlatform.CpuArchitecture: ARM64`; backend task definition has exactly the five `Secrets` names and no `POSTGRES_PASSWORD`/`SECRET_KEY` in `Environment`; ECS services have `DeploymentCircuitBreaker: { Enable: true, Rollback: true }`; ALB security group has exactly one ingress rule (TCP 80) and the database security group ingress references only the backend security group; CloudFront default behaviour uses the `CACHING_DISABLED` policy id and `redirect-to-https`; OIDC role trust `sub` conditions contain only this repository; budget exists with the e-mail subscriber; `prod` cluster has `DeletionProtection: true`.
- **Alternatives considered**: Jest (new dependency; `node:test` already used in the repo); snapshot tests only (brittle, do not state the security property).

## R13. Logs and cost controls

- **Decision**: One `logs.LogGroup` per service per environment (`/misiops/<env>/<service>`), `retention: ONE_MONTH`, `removalPolicy: DESTROY`, `ecs.LogDrivers.awsLogs`. One `budgets.CfnBudget` per environment: `COST`, monthly, limit 60 USD, notifications at 80 % actual and 100 % forecasted to the `alertEmail` context value (required; `cdk synth` fails without it).
- **Rationale**: FR-016, FR-018, NFR-003 (eval gap 4: the recipient is a required parameter). Container Insights is off (adds metric cost; out of scope).
- **Alternatives considered**: OpenSearch/Grafana (out of scope); AWS Cost Anomaly Detection (useful later, not a budget).

## R14. Stacks, region and parameters

- **Decision**: `infra/bin/misiops.ts` instantiates `MisiOps-Foundation` (account-wide: OIDC provider, deploy role, ECR repositories) and `MisiOps-<env>` (`FoundationStack`, `EnvironmentStack` in `infra/lib/`). Region `us-east-1`, account from `CDK_DEFAULT_ACCOUNT`. Context keys: `env` (`dev`|`prod`, required for the environment stack), `imageTag` (required), `alertEmail` (required). Stack outputs: `PublicUrl` (CloudFront domain), `AlbDnsName`, `BackendLogGroup`, `FrontendLogGroup`; Foundation outputs: `DeployRoleArn`, `BackendRepositoryUri`, `FrontendRepositoryUri`.
- **Rationale**: Two stack classes are the minimum that separates "once per account" from "once per environment" (spec FR-002); `us-east-1` is the cheapest region with full free tier and where the CloudFront prefix list and default certificate need no extra setup. Required context values fail fast at synth instead of deploying a half-configured environment.
- **Alternatives considered**: Separate network/data/app stacks (more cross-stack references than value at this size); CDK Pipelines (self-mutating pipeline in CodePipeline, duplicates what GitHub Actions already does).

## R15. Post-deployment verification

- **Decision**: After `cdk deploy`, the workflow reads `PublicUrl` from the stack outputs (`--outputs-file`) and runs a smoke script `infra/scripts/smoke.sh <url>`: `GET /` expects 200 and the string `MisiOps`; `GET /openapi.json` expects 200 and `"openapi"`; then 20 sequential requests to each, computing p95 of `curl -w %{time_total}` and failing above 2 s. The script has a Bash test with a stubbed `curl` (same pattern as `security/tests/test_upload_to_defectdojo.sh`).
- **Rationale**: FR-017, NFR-009, SC-009, and Constitution II (scripts have tests). `/openapi.json` is used instead of the backend's `/` because at the public address `/` routes to the frontend.
- **Alternatives considered**: ZAP against the deployed URL (out of scope); CloudWatch Synthetics canary (recurring cost).

## R16. Repository housekeeping affected by this feature

- `AGENTS.md` and `constitution.md` repository-structure trees gain `infra/`; `.github/workflows/sdd-enforcer.yml` and `.githooks/pre-push` treat `infra/` as implementation code (same grep as `frontend/|backend/`); `.gitignore` gains `infra/cdk.out/` and `infra/node_modules/`; `README.md` links `docs/deployment/README.md` (FR-019); `.github/pull_request_template.md` unchanged.
